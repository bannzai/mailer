# 通知枠 (フィルタルール) と判定エンジン

issue #9 で追加した通知枠の仕様のうち、issue に書かれていない部分 (状態の始まり方・終わり方、枠の優先順位、既定値) をここに記録する。コードが正 (`Sources/MailerCore/Notification/`)。ここには決めたことと根拠だけを書く。

## 枠と判定

- 枠は名前・条件 (差出人アドレス / ドメイン / 件名 / ラベル / Jev の判定結果の AND) ・ポリシー (即時 / interval ごとにまとめる / 通知しない) を持ち、`notification-rules.json` に配列で保存する
- 判定 (`NotificationEngine.decide`) は新着メール集合・枠定義・前回の状態・現在時刻から「今すぐ通知するメール」「次回まで保留するメール」「永続化する次の状態」を返す純粋関数。OS の通知配信 (#10) から分離する
- 状態 (`notification-state.json`) は枠の名前をキーに、最終通知時刻と保留中メール ID をアカウント別に持つ。同名の枠は状態を共有してしまうため、保存・読み込みで拒否する

## 決めたこと

| 決めたこと | 根拠 |
| --- | --- |
| どの枠にも合致しないメールは即時通知 | issue #9 の完了条件「デフォルト挙動 (即時通知) が定義されている」。枠を 1 つも設定していない状態で通知が届かないと、Gmail 公式アプリの通知を本アプリに一本化する運用 (#10) が成立しない |
| 枠は配列の並び順で先頭から評価し、最初に合致した枠に属する (先勝ち) | issue に優先度の指定が無い。既存の `accounts.json` と同じ「保存した並びがそのまま意味を持つ」形に揃え、優先度フィールドを足さない |
| バッチ枠で一度も通知していない時は、最初の 1 通を即時に出して時計を始める | issue に初回の扱いが無い。#10 の運用 (Gmail の通知を切って本アプリに一本化) では、枠を設定した直後の最初のメールが interval 分 (issue の例で最大 12 時間) 遅れると通知が消えたように見えるため、最初の 1 通で時計を始める。代案 (最初の 1 通も interval 待つ) に変える時は `NotificationEngine.decide` の `.batch` 分岐の `lastNotifiedAt == nil` の扱いと `batchRuleNotifiesFirstArrivalImmediately` テストを変える |
| 枠のポリシーを後から変えても保留中メールを取りこぼさない。即時枠は保留中 + 新着を全件配信し、通知しない枠は保留を破棄する | Codex レビュー (PR #27) の指摘。バッチから即時に変えると保留が消え、バッチから通知しないに変えると保留が残り続けていた |
| `--batch-hours` の上限は 8760 (1 年) | 1 年を超える間隔は通知しない枠と変わらない。巨大値は一覧の時間表記で Int に収まらず落ちた (PR #27 の観点レビューの指摘) |
| 条件の値に空文字・空白だけの文字列は指定できない | 空のシェル変数が `--subject ''` のように渡ると、空文字の部分一致で全メールに合致する枠が保存される (PR #27 の Codex レビューの指摘) |
| アカウントを削除すると、そのアカウントの通知状態も消す | 同じアドレスで再追加した時に古い保留と最終通知時刻が使われないため (PR #27 の Codex レビューの指摘)。判定結果 (`classifications.json`) はメール ID に紐付き再追加後も正しいので消さない |

## Jev の判定結果を条件に使う時

分類の仕様 (送る本文の範囲・保存する項目・3 帯の閾値・不達時の扱い) は `documents/inquiry-classification.md` と issue #28 を正とする。枠の条件としては、判定が無いメール (API 不達・未判定) と不確実帯の判定は分類条件を持つ枠に合致せず、残りの枠と既定の即時通知に流れる。
